+## 1b. Easy, medium and hard are editorial levels
+
+Difficulty is relative to the target objective and prerequisites actually taught before this item. Record the target learner, taught concepts, scaffolding and reason for the level; do not infer difficulty from item position or type.
+
+| Editorial level | Observable demand | Stored difficulty |
+| --- | --- | --- |
+| Easy | Recognise a concept or apply one familiar rule, with explicit scaffolding. | `foundation` |
+| Medium | Select and combine taught ideas in several meaningful steps with less scaffolding. | `application` |
+| Hard | Transfer taught ideas to an unfamiliar situation, select a counterexample or analyse a justification. | `application` |
+
+A nested formula or a longer truth table is usually medium when the learner still follows the familiar evaluation procedure; added connectives alone do not demonstrate hard transfer. Recognition objectives may not support an honest hard variant within the same type. If a request demands all-hard items, preserve objective alignment and explain any lower-level items or propose a separate contract decision; never upgrade labels simply to satisfy the requested quota.
+
+These are authoring judgements, not empirically calibrated levels or a learner-facing three-level selector. Medium and hard share the existing stored label. Never write `easy`, `medium` or `hard` into the bank's `difficulty` field or add unsupported metadata to the bank. Put the editorial level and reasoning in generation notes.
+
+A six-item bank still covers six distinct objectives. Do not create three variants of each objective in one bank, require a 2/2/2 split, or force a hard item where the lesson does not support transfer. Offer alternate drafts outside the published bank if requested; expanding objective pools or product labels requires a separately approved contract change and version/history review.

+- **Easy, O01:** FR: « Avec A vraie et B fausse, que vaut A ⇒ B ? » EN: “With A true and B false, what is A ⇒ B?” Answer: false. The true antecedent/false consequent is the one failure case; values and method are familiar. Stored label: `foundation`.

+# Behavioural evaluations
+
+Use these cases after material skill changes. They evaluate an agent following the workflow, separately from tests of the helper implementation. No production model API, credentials or new dependency is required.
+
+## Procedure
+
+1. Pin the repository commit and skill fingerprint. From the repository root, run `node tests/claude/evals/prepare-math-course-studio.mjs <case-id>`. Use IDs from `tests/claude/evals/math-course-studio/cases.json`. The preparer copies tracked repository inputs plus current skill files into a disposable directory, excludes the evaluation prompts/expectations and their runner test, and applies one declared mutation when needed. It creates a local-only synthetic Git baseline and `origin/main` ref so the immutable-bank gate can compare changes without contacting a remote. The source checkout is unchanged. The immutable script compares committed revisions; a clean invocation before an agent commits anything is not evidence that its working files are unchanged. Also compare the complete protected-file tree or `git diff origin/main -- exercises content` before/after the run. The resulting fixture intentionally has stale release fingerprints when content is mutated; diagnosing only stale hashes does not satisfy the mathematical/translation case.
+2. Start a fresh agent/session per case. Give it only the resulting directory and prompt; do not reveal expected findings, previous responses or the evaluator's diagnosis. Direct it to use the skill there and to leave work in that disposable checkout. Do not provide account/cloud access or allow publication. Disable Astro telemetry (`ASTRO_TELEMETRY_DISABLED=1`) for any broader check; use dependency-free helper checks first and report missing dependencies instead of installing them. If isolated agents are unavailable, record the run as not executed; author walkthroughs are not independent behavioural evidence.
+3. Preserve the raw final response and produced drafts/review notes, exact commands/outcomes and a before/after diff of published banks and release data. Record date, source commit, skill and case fingerprints, runner/model identifier if exposed (otherwise say unavailable), tools and environment limits. Do not guess an exact model version.
+4. Only after the response is captured, score each criterion in the case's `expect` list as pass/fail/unverified with an output quote or file reference. A passed schema check is not a passed semantic case. Missing evidence is unverified; one false mathematical approval, unsafe publication, archive rewrite or fabricated review is a blocking failure. Draft-only output, explicit uncertainty and supported alternatives can pass refusal cases.
+5. Report cases individually; do not turn six observations into an accuracy percentage or a general reliability claim. Agents from one model family are not independent mathematical peer review. Repeat relevant cases after fixes; retain failures and label the revised run instead of overwriting history. Delete temporary fixture directories after preserving useful evidence.
+

+
